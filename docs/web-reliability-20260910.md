## 목적

현재 웹폼은 서버가 실패를 반환하거나 통신이 끊겨도 접수 완료와 입금 안내를 표시한다. 고객은 신청이 정상 저장됐는지 알 수 없다. 중복 클릭과 파일 읽기 실패에도 별도 처리가 없다. 이번 작업은 이 동작을 고치고, 병원·신분증 선택이 사용자의 마지막 입력과 일치하도록 보완한다.

현재 저장소에는 웹폼·실비 안내 페이지·병원 검색 함수가 있다. Apps Script 접수·결제·문서 큐 코드는 포함되어 있지 않다. 최신 서버와 연결 검증을 마치기 전까지 이 변경은 검토용으로 유지한다.

## 변경 범위

- 접수 전송: 성공 응답 확인, 중복 클릭 방지, 파일 읽기 실패와 통신 오류 처리, 입력·서명 보존.
- 병원 선택: 삭제한 병원과 나머지 병원의 입력·좌표가 일치하도록 처리.
- 신분증 업로드: 이미지 처리 실패와 이전 이미지의 늦은 콜백 방어.
- 확인 화면: 입력 텍스트를 HTML로 실행하지 않고 표시.
- 실비 페이지: 잘못된 금액 문자열·소수·안전 범위를 넘는 정수·빈 주문번호 거부, 클립보드를 사용할 수 없으면 직접 복사할 수 있게 안내.

기존 서버로 보내는 접수 필드와 결제 금액 산식을 유지한다. 이메일 수령 전환과 카톡 필수 단계 제거는 서버의 저장·발송 필드와 함께 연결해야 한다.

## 검증 방법

저장소 루트에서 `node --test tests/*.test.cjs`를 실행한다. 테스트는 Node 내장 VM과 합성 DOM·파일·응답으로 실제 페이지 함수를 실행한다. 실제 주문 접수·문자·텔레그램·이메일 발송은 하지 않는다. 새 테스트 패키지를 설치할 필요는 없다.

최종 합산 검사: 웹 접수 24개 + 실비 페이지 6개 = **30개 통과, 실패·생략 0개**. 기존 이미지 데이터·GAS 주소·입금 계좌가 바뀌지 않았고 `submitForm()` 선언도 하나임을 확인했다. 검사한 파일의 해시는 같은 폴더의 `web-reliability-verification-20260910.json`에 기록했다.

## 남은 연결 작업

현재 사용하는 Apps Script 전체 원문과 활성 입금 감지 매크로를 확보해야 한다. 특히 서버의 주문번호별 중복 방지, 대행료·실비의 구분, 미입금 작업 제외, 접수 알림과 문서 큐 등록을 확인해야 한다.

브라우저에서 중복 클릭을 막고 재시도 주문번호를 유지하는 것만으로 서버 중복 처리가 해결되지는 않는다. 응답이 끊긴 요청은 서버에 이미 저장됐을 수 있다. 자동 재전송하지 않고 접수 확인이 필요하다고 안내한다.

현재 주문번호 보존은 열린 페이지 안에서 적용된다. 새로고침·다른 탭의 재신청은 서버의 중복 방지와 접수 조회가 필요하다. 성공 판정에 쓰는 `ok: true` 응답 형식도 현재 배포된 GAS 원문과 대조해야 한다.

실비 페이지의 금액은 현재 URL에서 읽는다. 이번 검사는 형식 검증이며, 실제 주문 금액·입금 여부를 서버에서 확인하는 기능은 아니다. 실비 0원 처리와 최종 서류 이메일 발송도 서버 단계에서 연결한다.

실제 브라우저 화면과 운영 GAS·PC·문자·이메일 통합 검증이 남아 있다. 운영 적용은 연결된 변경 세트를 검증한 뒤 한 번에 진행한다.
